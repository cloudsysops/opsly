# ADR-028: Agent API Routing Consolidation

## Status: DRAFT (requires architecture decision)

## Context

The orchestrator currently exposes agent routes (hive, mcp, terminal) via inline HTTP server (`health-server.ts`), while the Next.js API app expects these routes to exist in `apps/api/app/api/*`.

This creates a **type-check blocker**: Next.js validator references routes that don't exist, causing build to fail.

### Current State

**Routes in orchestrator:**
```
POST   /internal/hive/objective
GET    /internal/hive/objective/[taskId]
POST   /internal/mcp/execute
GET    /internal/mcp/catalog
POST   /internal/terminal/start
...
```
Live in: `apps/orchestrator/src/health-server.ts`

**Type validator expects:**
```
apps/api/app/api/admin/agents/hive/objective/[taskId]/route.js
apps/api/app/api/admin/agents/mcp/catalog/route.js
apps/api/app/api/admin/agents/terminal/[agentId]/sessions/[sessionId]/output/route.js
...
```
From: `.next/types/validator.ts` (autogenerated by Next.js)

**Reality:** These routes don't exist in `apps/api`. Validator is out of sync.

---

## Problem Statement

1. **Type-check fails in CI:** 14 TS2307 errors (module not found)
2. **Confusion about where agent APIs live:** split between 2 apps
3. **No single source of truth:** OpenAPI spec, orchestrator routes, and API spec diverged
4. **Blocked CI/CD:** Can't merge PRs without fixing cache

---

## Decision Options

### Option A: Move Agent Routes to `apps/api`

**Description:**  
All agent endpoints (`/api/admin/agents/*`) live in Next.js API.  
Orchestrator becomes internal queue worker only (no HTTP routes for agents).

**Pros:**
- Single source of truth (Next.js router)
- Type validator is happy
- OpenAPI spec matches code
- HTTP contract explicit in app/api/

**Cons:**
- Refactoring effort: 4-6 hours
- Orchestrator loses direct HTTP (adds gateway layer)
- Might break existing integrations if agents hit orchestrator directly
- Requires changes to local agent workers (LocalClaudeWorker, etc.)

**Impact:**
- 11 new routes in `apps/api`
- health-server removes agent route handlers
- orchestrator becomes "internal-only"
- CI/CD passes (validator happy)

**Effort:** 4-6 hours (routes + tests + integration)

---

### Option B: Exclude Orchestrator from Next.js Type Validation

**Description:**  
Tell Next.js validator to ignore orchestrator routes entirely.  
Routes stay where they are; validator learns not to look for them.

**Pros:**
- Minimal code change (tsconfig + validator config)
- Fastest fix (1 hour)
- No refactoring
- Routes stay where they're currently working

**Cons:**
- Validator coverage reduced (orchestrator routes unchecked)
- Doesn't solve the "where do APIs live?" confusion
- Architectural debt remains
- Future developer confusion

**Impact:**
- 1-2 lines in `tsconfig.json` or `next.config.js`
- Routes remain in orchestrator
- CI/CD passes (validator disabled for orchestrator)

**Effort:** 1 hour (config only)

---

### Option C: Clean Up OpenAPI Spec to Match Reality

**Description:**  
Update `.next/types/validator.ts` generation to only include routes that actually exist.  
Clean up the spec to reflect current architecture.

**Pros:**
- Documents what we actually have
- Validator reflects reality
- Identifies orphaned route definitions

**Cons:**
- Still doesn't answer "where should agent APIs live?"
- Requires understanding of spec generation
- Temporary fix (problem reappears if routes move)

**Impact:**
- Rebuild `.next` types cleanly
- Update OpenAPI spec
- Routes remain in orchestrator

**Effort:** 2-3 hours (investigation + spec cleanup)

---

## Recommendation

**Suggest: Option A (move to API)** with phased approach:

**Phase 1 (1-2 weeks):**
1. Create `ADR-028-adopted.md` with decision
2. Move high-use routes first (mcp/execute, hive/objective)
3. Keep orchestrator routes as fallback (with deprecation warning)
4. Add integration tests for both paths
5. Deploy to staging

**Phase 2 (1 week):**
6. Monitor usage logs for orchestrator routes
7. Migrate remaining low-use routes
8. Remove fallback routes
9. Deploy to production

**Phase 3 (same-day):**
10. Remove orchestrator HTTP handler
11. CI/CD passes

This gives us a clean architecture + time to validate.

## Rejection Criteria

- If agents MUST run in orchestrator (isolation/security reason)
  → Choose Option B
- If refactoring cost is too high
  → Choose Option B or C
- If we want to deprecate orchestrator entirely
  → Choose Option A with full migration
